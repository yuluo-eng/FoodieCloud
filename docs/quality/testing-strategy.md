# 测试策略（Testing Strategy）

> 目标：在保证交付速度的同时，降低回归风险与线上故障率。

## 1. 测试分层

## 1.1 单元测试（Unit Test）

- 作用：验证核心业务逻辑。
- 范围：`service` 层优先，覆盖复杂规则与边界。
- 特点：执行快、定位准、可在本地频繁运行。

## 1.2 集成测试（Integration Test）

- 作用：验证模块协同（数据库、缓存、外部依赖）。
- 范围：关键业务链路、事务边界、序列化协议。
- 特点：贴近真实运行环境。

## 1.3 接口测试（API Test）

- 作用：验证 API 契约与错误处理一致性。
- 范围：核心接口（创建、更新、支付、查询）及权限场景。
- 特点：可用于回归与发布冒烟。

## 2. 覆盖优先级

优先覆盖以下场景：

1. 高价值路径（下单、支付、状态变更）。
2. 高风险路径（事务、并发、权限、幂等）。
3. 历史易出错模块（根据线上复盘与缺陷统计）。

## 3. 最低门禁建议

- 单元测试：新增业务逻辑必须有对应测试。
- CI：测试全部通过才允许合并到 `develop`。
- 发布前：必须完成冒烟测试与关键路径回归。

## 4. 用例设计原则

- 正常流程：输入合法时输出正确。
- 异常流程：参数非法、状态非法、资源不存在。
- 边界流程：空值、最大值、最小值、重复请求。
- 权限流程：未登录、无权限、越权访问。

## 5. 测试数据与环境

- 使用独立测试库，避免污染开发数据。
- 构建可重复执行的初始化脚本。
- 对外部依赖优先 mock；必要时使用沙箱环境。

## 6. 发布验证（冒烟清单）

- 应用启动正常，核心依赖可连接。
- 核心 API 可用，状态码与业务码正确。
- 关键日志与监控指标正常上报。
- 回滚预案已演练或可快速执行。

## 7. 质量度量建议（DORA 视角）

- 部署频率（Deployment Frequency）
- 变更前置时间（Lead Time for Changes）
- 变更失败率（Change Failure Rate）
- 平均恢复时间（MTTR）

每次迭代复盘一次，持续优化测试资产与发布流程。
