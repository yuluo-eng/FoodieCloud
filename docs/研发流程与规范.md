# 研发流程与规范（整合版）

本文件整合了分支策略、代码评审、CI 门禁与测试策略，作为团队协作的统一入口。

## 1. 标准开发流程

1. 基于需求创建 Issue，明确验收标准与边界。
2. 从 `develop` 拉取功能分支：`feature/*`。
3. 开发完成后补充测试并自检。
4. 提交 PR（关联 Issue、说明风险与回滚）。
5. 通过 Review + CI 后合并到 `develop`。
6. 通过 `release/*` 分支完成发布，最终合并至 `master` 并打 tag。

## 2. 分支与命名策略

- `master`：生产稳定分支
- `develop`：开发集成分支
- `feature/*`：功能开发
- `release/*`：发版准备
- `hotfix/*`：线上紧急修复

示例：

- `feature/rider-auth-hardening`
- `release/1.2.0`
- `hotfix/order-status-bug`

## 3. 提交与 PR 规范

建议使用 Conventional Commits：

- `feat:` 新功能
- `fix:` 缺陷修复
- `refactor:` 重构
- `test:` 测试
- `docs:` 文档
- `chore:` 工程维护

PR 基本要求：

- 说明变更目标、影响范围、测试方式、风险与回滚方案
- 一个 PR 聚焦一个主题，避免混入无关修改
- 优先控制在可审阅规模（建议 200-400 行核心改动）

## 4. 代码评审清单

- 正确性：需求覆盖、边界条件、异常处理
- 架构设计：分层合理、避免重复、接口兼容
- 数据事务：事务边界清晰、并发与幂等可控
- 安全性：鉴权授权、输入校验、敏感信息脱敏
- 可观测性：关键日志、上下文、指标与告警
- 测试：主流程、异常流程、权限流程覆盖

## 5. 分支保护与 CI

对 `master` 与 `develop` 建议启用：

- 必须通过 PR 合并（禁止直接 push）
- 至少 1 个 Approve
- 必须通过状态检查
- 所有 review 对话已解决
- 建议使用 squash merge

CI 最低检查项：

- `mvn -q -DskipTests compile`
- `mvn -q test`
- `mvn -q -DskipTests package`

## 6. 测试策略（最小闭环）

- 单元测试：重点覆盖 `service` 复杂规则
- 集成测试：覆盖事务、数据库与模块协同
- 接口测试：覆盖核心 API 契约与错误场景
- 发布冒烟：覆盖关键业务链路与权限链路

优先覆盖：

1. 高价值流程（下单、支付、状态变更）
2. 高风险流程（并发、权限、幂等、事务）
3. 历史高故障模块
