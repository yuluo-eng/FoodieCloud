状态检索：根据用户名查询数据库。若查询结果为空，返回“账号不存在”；若查询到员工，则比对加密后的密文。状态控制：系统必须校验 status 字段。若 status 为 0，则拒绝登录并返回“账号已锁定”提示。上下文绑定：验证通过后，将员工 ID 存入 HttpSession，并作为后续所有请求的唯一身份凭证。输出规范：成功时返回包含员工基本信息的通用响应对象 R<Employee>。2. 员工信息维护与 AOP 审计新增逻辑：管理员在后台录入新员工。系统在 Controller 层利用 RequestBody 接收实体。在 Service 层执行 save 前，必须进行唯一性校验（如手机号、身份证号、账号名）。AOP 自动填充机制：系统通过 MyMetaObjectHandler 拦截实体操作。在执行 insert 动作前，利用 ThreadLocal 从当前线程中提取操作人 ID，自动注入 createTime、updateTime、createUser 和 updateUser 四个审计字段，确保每一条记录都具备可溯源性。编辑与精度处理：在修改员工信息时，前端回传的 Long 型 ID 必须通过消息转换器映射为 String，以防止 JavaScript 精度坍塌导致的“修改失败”或“找不到记录”异常。3. 账号状态的原子性切换业务逻辑：管理员具备启用或禁用员工的权限。处理机制：系统通过 updateById 方法实现。在底层执行时，系统并非全量更新，而是通过 MyBatis-Plus 生成的动态 SQL，仅对 status 和审计字段进行更新，确保了数据库执行的原子性与高效性。2.3.2 分类管理子系统分类模块是菜品和套餐的基石，承载着系统展示层级的逻辑。1. 分类的新增与权重排序逻辑分类类型：分为“菜品分类”和“套餐分类”，由 type 字段区分。排序机制：系统引入 sort 字段作为排序权重。前端在展示分类列表时，queryWrapper.orderByAsc(Category::getSort).orderByDesc(Category::getUpdateTime)双重排序逻辑保证了：权重小的排在前，权重相同时按更新时间倒序排列。2. 级联校验与逻辑一致性
删除业务约束：删除分类是一项高风险操作。系统严禁直接调用删除接口，必须执行以下三步校验：第一步：关联菜品检查。调用 DishService 执行 count 查询，判断当前分类 ID 下是否有存量菜品。第二步：关联套餐检查。调用 SetmealService 执行同样的操作。第三步：异常阻断。若上述任意一项计数大于 0，则通过抛出 CustomException强制中断事务。该异常由 GlobalExceptionHandler 捕获并向前端发送 0 状态码及错误文案，防止产生“孤儿数据”。2.3.3 菜品管理子系统菜品管理涉及到复杂的数据关联与文件处理。1. 菜品新增与关联保存数据结构：菜品信息分散在 dish和 dish_flavor中。事务处理：新增菜品时，由于涉及到两张表的写入，必须在 Service 层方法上添加 @Transactional 注解。系统首先保存菜品基本信息以获取主键 ID，随后将该 ID 遍历设置给口味列表，最后批量插入 dish_flavor 表。2. 图片上传与下载流处理上传流程：系统接收 MultipartFile。为防止文件名冲突，采用 UUID 重命名，并将文件持久化到配置的本地磁盘或云存储路径中。回显流程：采用 ServletOutputStream 将图片以文件流的形式输出给前端。这种方式比直接暴露静态资源路径更具安全性，且易于后续扩展图片水印或压缩逻辑。
2.3.4 套餐管理子系统套餐由多个菜品组合而成，体现了系统的业务组合能力。组合逻辑：套餐管理需维护 setmeal 与 setmeal_dish 的一对多关系。停用逻辑：当套餐被停用时，前端展示需实时同步。在删除套餐前，系统需校验套餐是否处于“禁售”状态，若套餐正在售卖中，则通过业务规则拦截删除指令。2.4 数据需求2.4.1 概念模型设计本系统的数据模型设计围绕餐饮业务的核心链路展开，主要涉及员工（Employee）、分类（Category）、菜品（Dish）与套餐（Setmeal）四个核心实体。Employee 实体作为系统的管理主体，具有独立性，主要记录账号凭证与状态。Category 实体作为业务分类的基石，与 Dish、Setmeal 均呈现出“一对多”的关联关系，即一个分类下可以挂载多个菜品或套餐。Dish 与 Setmeal 之间通过业务逻辑产生组合关系。为确保系统的灵活性，菜品单价与套餐总价均采用 BigDecimal 类型存储，以保证金额运算的精确度。2.4.2 逻辑结构设计实体名称（表名）核心字段字段数据类型约束/备注Employee（员工表）idusernameid_numberBIGINTVARCHARVARCHARid：主键，自增username：唯一约束id_number：身份证号，存储时需脱敏Category（idtypenamesortBIGINTINTVARCHARINTid：主键，自增type：分类类型（1 = 菜品分类，2 = 套

2.5 性能需求为了保障“瑞吉外卖”系统在后台管理场景下的流畅体验，提出以下非功能性性能要求：响应时效性：对于常规的 CRUD 操作，系统的后端响应时间应控制在 200ms 以内；对于涉及多表联查的分页请求，在高并发情况下，P99 响应时间不应超过 1s。吞吐能力：系统应能支持至少 50 个 管理员同时在线操作而不产生明显的线程阻塞或内存溢出风险。数据一致性：涉及菜品、套餐及口味关联的多表操作，必须严格遵循数据库 ACID 事务原则，确保在发生网络抖动或异常时，数据状态能够自动回滚。
